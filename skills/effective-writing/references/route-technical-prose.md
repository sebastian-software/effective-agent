# Route: Technical Subject-Matter Writing

Use this route for writing where correctness of the technical claim is part of
the editorial job, such as engineering blog posts, technical articles,
explainers, technical case studies, public technical project pages, technical
concepts, design proposals, and comparable technical writing.

## Guidance

[Technical subject-matter writing](technical-subject-matter.md) covers source
ownership, technical propositions, terminology, and drafting a bylined article
from the author's material.

For a technical concept, a design proposal, or an article that describes one,
run the precision pass in
[Technical subject-matter writing](technical-subject-matter.md#run-a-precision-pass-on-concepts).
The pass applies in any language;
[Technical concept precision](technical-concept-precision.md) shows it on German
examples.

When a blog post needs a sharper angle, a more engaging explanation, or an
ending, consult the relevant section of the [editorial field guide](editorial-field-guide.md).
Its local readings and worked examples can be used offline.

Use [Assignment and evidence](nonfiction-assignment.md) only when a substantial
piece needs briefing or source planning.

## Apply

- For a new blog post, read the publication's brief and voice guidance when
  available. Draft in its source language for the reader it names. Use the
  [article drafting guidance](technical-subject-matter.md#draft-from-the-material)
  to carry the author's perspective into the first draft.
- Keep the technical claim inside what the supplied evidence supports.
  Check measurements, incident timelines, and version behavior at the source.
- Prefer a worked example to an abstraction when both would fit.
- Honor explicit style and controlled-language requests on the first pass.
  Explain a material tradeoff briefly without requiring reconfirmation or
  substituting your preferred register. Use `effective-delivery` for a named
  controlled-language standard; preserve technical meaning and claim
  conformance only when verified.
- A long-form concept stored as an issue body or tracker document stays on this
  route. Use the formal register of its repository or channel, not Metro
  English; a short team comment about it belongs to
  [Metro English](route-metro-english.md).

## Cross-links

- When correctness must be derived from a repository, public interface,
  executable example, migration contract, or documentation toolchain, the
  artifact is technical documentation and belongs to `effective-delivery`. Keep
  the governing idea, editorial structure, and public voice here when the
  artifact remains an article or long-form page.
- Only the wording of a concept or proposal belongs here. The content and
  review of an application concept belong to `effective-product`; design
  decisions and architecture-proposal reviews belong to `effective-engineering`.
- Page hierarchy, interface copy, accessibility, and browser implementation of
  the published page belong to `effective-web`.
